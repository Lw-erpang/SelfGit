## 1. 产品概述与范围

### 1.1 一句话定位
面向个人开发者的 Android 端"私有 Gitea 应用商店"：登录自有 Gitea（如 NAS Docker 部署 `http://192.168.x.x:3000`），浏览全量仓库、安装/更新 APK、从手机上传 APK 并维护每个应用的历史版本库。

### 1.2 范围内（In Scope）
- 连接**单个**自托管 Gitea 实例；多主机仅作为"配置可切换"支持，不支持同时在线
- 登录：密码引导 + 令牌运行（混合模式），支持 2FA 降级
- 仓库主备地址：局域网 HTTP（主）+ DDNS HTTPS（备）
- 仓库全量列表、Release 列表、Markdown 基础渲染、APK 下载与安装
- 手机上传 APK：解析元数据 → 建 tag/Release（含修改日志）→ 附件上传 → 历史版本聚合
- 启动时刷新 + 前台手动/下拉刷新；**不做任何后台同步**
- 安装后端四种：系统默认安装器 / Shizuku 静默安装 / Root 静默安装（libsu）/ **第三方安装器**（用户自选外部安装器 App，如"芝麻粒"等，安装请求转发给该应用）

### 1.3 范围外（Out of Scope，明确不做）
- 后台定时轮询、推送通知、Webhook 接收
- GitHub/GitLab/Codeberg 等任何其他 Forge
- 断点续传上传
- 多账号同时登录、组织/团队权限管理界面
- 公开发布/应用市场功能（发现、热门、评分）

## 2. 总体架构

- **形态**：单机 Android App，无自有服务端，直连 Gitea REST API（`/api/v1`）。
- **技术栈**（建议，评审时可调）：Kotlin + Jetpack Compose + Room + OkHttp/Retrofit + Android Keystore（+ 可选 Shizuku）。
- **模块划分**（逻辑分层，非代码结构）：
  1. `主机与认证`：主备地址管理、健康探测、令牌生命周期（本文档第 3、5 章核心）
  2. `浏览`：仓库列表、详情、Release 列表、下载安装
  3. `上传`：APK 元数据解析、条目/tag 管理、附件上传、失败恢复
  4. `同步缓存`：Room 本地缓存 + 启动刷新管线（前台限定）
  5. `设置`：配置项、配置导入导出、令牌管理界面

## 3. 登录与运行机制（核心）：密码引导 + 令牌运行

### 3.1 模式总览

| 阶段 | 凭证 | 传输方式 | 说明 |
|---|---|---|---|
| 引导期（一次性） | 账号密码 | HTTP Basic Auth，仅用于调用"创建令牌"接口 | 密码**不落盘**，用完即弃 |
| 运行期（常态） | 访问令牌 | 请求头注入（Authorization: token …） | Keystore 加密存储，可吊销 |

设计原则：**密码只在登录瞬间出现在内存与传输层；运行期全部以令牌通行；令牌与主机配置分离存储，主机配置变更不自动销毁令牌。**

### 3.2 P1 首次登录主流程

1. 用户进入"添加主机"：填写主机地址（含主备，见第 5 章）+ 显示名。
2. App 以**免认证轻量探测**（GET `/api/v1/version`）验证主机可达，失败时按主备顺序尝试并报告结果。
3. 认证二选一：
   - **密码引导**：输入账号密码 → Basic Auth 调用"为当前用户创建访问令牌"接口（POST `/api/v1/users/{owner}/tokens`）：
     - 创建两个令牌：`giteahub-ro`（仅 repository 读，用于浏览/下载）与 `giteahub-rw`（repository 读写，仅上传时启用）；
     - 令牌名带 App 标识与时间戳，便于用户日后在 Gitea 网页端识别与吊销；
     - 创建成功 → 令牌加密落盘 → **立即从内存清除密码** → 用 ro 令牌做一次自校验（GET `/api/v1/user`）→ 进入主界面。
   - **直接粘贴令牌**：用户在 Gitea 网页端自建令牌后粘贴；App 校验格式与权限（读取令牌 scope），权限不足给出明确提示。
4. 完成后记录"认证方式"与令牌元数据（名称、scope、创建时间；**不记录令牌明文副本以外任何敏感信息**）。

### 3.3 令牌使用规则

- 所有 API 请求经统一拦截器注入令牌；浏览类请求固定用 ro 令牌；上传类请求在发起前切换为 rw 令牌，结束后切回。
- rw 令牌可配置为"使用时确认"：每次上传前弹出一次性确认（可关闭）。
- 令牌存储：Android Keystore 加密，随 App 卸载销毁；配置导出**默认不包含令牌**（见 4.3）。

### 3.4 令牌失效处理（P6 流程）

**失效判定信号**：HTTP 401（令牌过期/吊销/账号变更）、HTTP 403（权限不足）、连续网络正常但认证失败 ≥ 3 次。

**处理策略**：

| 信号 | 判定 | 用户动作 | App 行为 |
|---|---|---|---|
| 401 | 令牌失效 | 重新认证 | **保留全部主机配置与本地缓存**，弹"重新认证"页：优先走密码引导重建令牌（旧令牌名提示用户去网页端手动删除）；支持直接粘贴新令牌 |
| 403（浏览） | ro 令牌权限被改窄 | 检查令牌 scope | 明确提示"令牌权限不足：需要 repository 读权限"，附 Gitea 网页端路径说明 |
| 403（上传） | rw 令牌缺失写权限 | 检查/重建 rw 令牌 | 上传终止，已创建的 Release 按失败流程处理（见 P4） |
| 403 + 指纹变化 | 主机地址指到了错误服务 | 检查主备地址 | 不自动清除配置 |

**明确不做的**：不自动重建令牌（避免无限重试风暴）；不静默删除本地缓存；不在失效时自动切换账号。

### 3.5 登录边界条件

- **2FA 已开启**：Gitea 对 Basic Auth 密码直连 API 会拒绝 → 密码引导必然失败 → App 检测到认证被拒且密码确系正确时，提示"账号已开启两步验证，请直接粘贴访问令牌"。
- **令牌重名**：Gitea 令牌名必须唯一 → 创建失败时自动追加随机后缀重试一次。
- **网络中途断开**：引导流程任一步骤失败都允许重试；令牌已创建但自校验失败时，按"令牌可能已创建"提示用户网页端检查，避免重复创建。
- **密码正确但账号被禁用**：等同 401 处理，提示联系管理员。

## 4. 安装与初始化配置（参考 Komi，多种配置方式）

### 4.1 首启引导（参考 Komi 的引导节奏）

首次启动 → 欢迎页（说明权限用途：安装/存储选择器）→ 引导完成主机配置（以下任一方式）→ 进入主界面（空态页提供示例说明）。

### 4.2 四种配置方式（按优先级）

| 方式 | 入口 | 内容 | 适用场景 |
|---|---|---|---|
| F1 手动表单（默认） | "添加主机" | 主机主备地址 + 账号密码/令牌 | 首次手工配置 |
| F2 剪贴板/分享识别 | 主界面"+"或外部"分享到 SelfGit" | 粘贴 `http://host:port/owner/repo` 或仓库页分享链接 → 解析出主机与仓库并预填表单（**不携带令牌**，令牌仍需登录步骤） | 从浏览器/聊天里复制地址快速添加 |
| F3 配置文件导入 | 设置 → 导入 | JSON 配置文件（结构见 4.3），可选是否包含令牌 | 换机迁移、多设备同步 |
| F4 二维码导入（可选，阶段 3） | "扫码导入" | 同 F3 内容的二维码 | 双端现场迁移 |

安全约束：F2/F3/F4 中若包含令牌，导入前必须明示"将导入一个访问令牌"并二次确认；公共剪贴板内容中的令牌识别到后立即提示建议清除剪贴板。

### 4.3 配置文件结构（逻辑字段，非代码）

```
配置文件 = {
  版本号,
  主机条目[] {
    显示名, 主地址{协议,地址,端口}, 备地址{...}或空,
    认证方式(密码引导/令牌), 令牌元数据{名称,scope,创建时间}(不含令牌明文),
    偏好设置(刷新防抖秒数,超时,仅WiFi下载等)
  },
  本地收藏/追踪映射(可选导出)
}
```

导出令牌为**显式选项**，默认关闭；导出文件建议用户自行妥善保管。

## 5. 仓库地址主备配置（局域网 HTTP / DDNS HTTPS）

### 5.1 配置结构

每个主机条目支持：
- **主地址**：局域网场景，如 `http://192.168.x.x:3000`
- **备地址**：DDNS/公网场景，如 `https://gitea.example.com`（端口可省略或自定义）
- 两地址必须指向**同一 Gitea 实例**（同一份账号与仓库数据）；App 不做数据一致性校验，由用户保证。

### 5.2 地址选择策略（P5 流程）

1. **记忆优先**：优先使用"最后成功地址"（持久化）。
2. **自动探测**：无记忆或记忆地址失败时，按 主 → 备 顺序探测，探测手段为免认证轻量请求（GET `/api/v1/version`），超时 5 秒。
3. **切换判定**：仅"连接类失败"（超时、DNS 解析失败、网络不可达、TLS 握手失败）触发备用地址切换；**认证失败不触发切换**（地址可达但凭证错误属于第 3 章问题）。
4. **手动切换**：设置与主界面状态条提供"当前生效地址"展示与手动切换入口；手动切换立即触发一次重新探测并刷新数据。
5. **会话内粘滞**：一次使用会话内探测成功后不再来回切换，避免抖动；下次启动重新按记忆优先策略执行。

### 5.3 HTTPS（备地址）边界

- 仅接受**系统信任的证书**（如 Let's Encrypt）；**自签证书不支持**（沿用 Komi 教训：Komi 强制系统信任链导致自签永久失败，本设计明确边界并提前告知用户）。
- DDNS 域名必须能在手机侧解析（公网 DNS A 记录指向内网 IP 亦可）。
- 主备地址协议可以不同（主 http、备 https）；App 按配置原样连接，不做自动升级。

## 6. 数据刷新机制（无后台同步）

### 6.1 原则

- **无 WorkManager / 无轮询 / 无推送**；数据新鲜度完全由"使用时"驱动。
- 本地 Room 缓存保存上次成功数据；无网或主机不可达时**展示缓存 + 显式标注数据时间**（如"数据更新于 2 小时前（缓存）"）。

### 6.2 启动刷新（自动）

- 触发：App 进入前台（onStart）且距上次成功刷新超过**防抖阈值**（默认 60 秒，可配）。
- 行为：并行拉取"我的仓库列表 + 已追踪应用的最新 Release 状态"；UI 先渲染缓存数据并叠加"刷新中"态，不阻塞浏览。
- 完成后：更新缓存与"数据时间"；发现新版本时在对应条目打更新角标（不弹系统通知——无后台即无通知场景）。

### 6.3 前台期间刷新（手动）

- 一键刷新按钮（全局）+ 下拉刷新（列表级）：两者共用同一刷新管线，刷新期间防抖避免重复请求。
- 上传成功后自动刷新对应仓库；安装成功后自动刷新追踪状态。
- App 进入后台超过阈值后再回前台，视同"启动刷新"重新触发。

### 6.4 生命周期边界

| 场景 | 行为 |
|---|---|
| 刷新中退出 App | 请求继续完成并写缓存，UI 无所谓（下次启动读缓存） |
| 刷新中主机不可达 | 静默失败，保留缓存 + 状态条提示"刷新失败：主机不可达（已切换备用地址？）" |
| 长时间驻留前台 | 提供"数据时间"展示，超过 30 分钟提示手动刷新 |
| 多主机配置 | 仅刷新当前生效主机 |

## 8. 核心流程编号

| 编号 | 流程 | 关键节点 | 关联章节 |
|---|---|---|---|
| P1 | 首次配置与登录 | 探测 → 认证（密码引导/令牌）→ 自校验 → 进入主界面 | 3.2、4.2 |
| P2 | 启动刷新 | 防抖判定 → 并行拉取 → 缓存更新 → 更新角标 | 6.2 |
| P3 | 浏览/下载安装 | 仓库列表 → 详情 → Release → 下载 → 安装（系统/Shizuku/Root/第三方） | 1.2 |
| P4 | 上传新版本 | SAF 选文件 → 解析元数据 → tag 查重 → 建 Release（含修改日志）→ 上传附件 → 失败清理 → 刷新 | 8.1 |
| P5 | 主备切换 | 探测 → 记忆优先 → 自动切换（仅连接类失败）→ 手动切换 | 5.2 |
| P6 | 令牌失效恢复 | 信号判定 → 保留配置 → 重新认证页 → 重建/换令牌 | 3.4 |

### 8.1 P4 上传流程细则（含一致性保障）

1. 选文件 → 解析（应用名、包名、versionName、versionCode、图标、架构）。
2. **查重**：按包名匹配已有条目 → 命中则提示"作为新版本上传到条目 X"；
3. tag 生成：按模板 `{应用名}-v{版本}`；与远端 tag 冲突时终止并提示（**不覆盖**，覆盖属 PC 端显式操作）。
4. 建 Release：描述预填修改日志模板（用户可编辑）；版本信息（包名/versionCode/架构）写入描述固定字段，供已装匹配与追溯。
5. 上传附件：单次 POST + 进度展示；**失败重试 ≤ 2 次**；
6. **失败清理**：Release 已建但附件最终失败 → 提示用户选择"删除空 Release"或"保留待手动补传"（默认建议删除）。
7. 成功后自动刷新对应仓库。

## 9. 异常处理矩阵

| 错误类别 | 典型场景 | 用户提示 | 系统行为 |
|---|---|---|---|
| 连接失败 | 超时/DNS 失败/拒绝连接 | "主机不可达（主）→ 已尝试备地址" | 触发 P5；写缓存保留 |
| TLS 失败 | 自签证书/域名不匹配 | "证书不受信任：仅支持系统信任证书（如 Let's Encrypt）" | 终止，不回退明文 |
| 认证失败 401 | 令牌过期/吊销 | "登录已失效，请重新认证" | 触发 P6，保留缓存 |
| 权限不足 403 | scope 被改窄/账号权限变化 | 指明缺失的权限与补救路径 | 按操作类型终止 |
| 上传中断 | 网络切换/信号弱 | "上传失败（已重试 2 次）：附件 87% 时中断" | 按 P4 第 6 步清理策略 |
| 解析失败 | 非标准 APK/XAPK | "无法读取应用信息：可能不是标准 APK" | 终止上传，允许改名仅存文件 |
| 服务器错误 5xx | Gitea 容器重启 | "服务端暂时不可用" | 指数退避重试 1 次，不切主机 |
| 版本冲突 | tag 已存在 | "版本 vX.Y.Z 已存在（上传于 …），不可覆盖" | 终止，建议改版本号 |

## 10. 边界条件清单

1. **空仓库**：目标仓库无任何提交时建 Release 会失败 → 上传时检测并提示"请先在网页端初始化仓库（自动创建 README）"。
2. **同名不同应用**：不同包名但显示名相同的条目 → 条目唯一键为**包名**，显示冲突时加包名后缀区分。
3. **超大文件**：>200MB 附件受 Gitea 服务端限制 → 上传前读取远端允许上限（或实测报错透传），提前告知。
4. **版本号不规范**：解析出的 versionName 不符合模板 → 允许用户编辑后继续，但警告版本比对可能失准。
5. **本地已装但远端无包名记录**（历史存量）：提供手动"链接追踪"（选择本机应用 + 选择远端仓库）补齐映射。
6. **仓库被删除/改名**：详情页 404 → 提示并从列表移除（缓存保留 24 小时以便恢复误删场景）。
7. **时钟偏差**：本机时间错误导致 TLS/令牌判定异常 → 检测系统时间偏差 > 5 分钟时提示校正。
8. **多设备并发上传**：无锁机制，靠 tag 查重兜底 → 撞车时后到者明确报错。
9. **Gitea 版本差异**：目标为 Gitea 1.20+（当前 NAS 为 1.28.x 量级，实测可用）；低版本 API 缺失以 404 透传并提示升级。
10. **App 被杀后重传**：上传无断点续传，进程被杀即从零开始（阶段 2 内可接受，文档明确记录）。

## 12. 安全与隐私说明

- **令牌**：Keystore 加密、按主机隔离、分级（ro/rw）、可随时在 Gitea 网页端吊销；导出配置默认不含令牌。
- **密码**：仅存在于引导请求的内存与传输层，不持久化、不写日志。
- **HTTP 明文（主地址）**：令牌与 APK 走明文传输，风险等级与现有浏览器直连方案相同；EasyTier 虚拟网流量自带加密可部分缓解。备地址建议启用 HTTPS。此取舍为用户已知悉的显式决策（2026-11-17 评估记录）。
- **无遥测**：App 不收集、不上报任何数据；崩溃日志仅本地留存。
